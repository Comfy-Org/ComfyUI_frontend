# A5 Architecture Review Findings

## Summary
This PR introduces a new `RemoteCombo` widget system powered by TanStack Query (vue-query). The architecture is generally sound with good separation of concerns between data fetching (`useRemoteOptions`), business logic (`useRemoteCombo`), and presentation (atomic Vue components). However, there are several areas requiring attention.

---

### [MEDIUM] RemoteComboContext has multiple responsibilities
- **File:** src/renderer/extensions/vueNodes/widgets/components/RemoteCombo/state.ts:6-21
- **Issue:** `RemoteComboContext` interface bundles together UI state (`isOpen`, `searchQuery`), data state (`items`, `filteredItems`), async state (`isLoading`, `isFetching`, `errorMessage`), and behavior (`refresh`, `select`). This violates the Single Responsibility Principle and makes the context harder to test and extend independently.
- **Fix:** Consider splitting into separate contexts: `RemoteComboUIContext` (isOpen, searchQuery, select), `RemoteComboDataContext` (items, filteredItems, isLoading, error), and passing behaviors via props or a separate actions interface.

---

### [MEDIUM] useRemoteCombo couples data fetching with UI filtering logic
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:45-163
- **Issue:** This composable mixes multiple concerns: remote data fetching orchestration, local search/filter logic, auto-select behavior, and state management for open/search. This tight coupling makes it harder to reuse individual pieces (e.g., filtering) elsewhere.
- **Fix:** Extract `useSearchFilter` as a separate composable that takes items and returns filtered items. Keep `useRemoteCombo` focused on orchestrating these pieces rather than implementing them all inline.

---

### [LOW] Global singleton pattern for QueryClient
- **File:** src/platform/remote/queryClient.ts:8-20
- **Issue:** `appQueryClient` uses a module-level singleton pattern with `let appQueryClient: QueryClient | undefined`. While the comment explains the rationale (auth-state teardown evicts cache), this pattern can cause issues in testing and makes it harder to reason about lifecycle boundaries.
- **Fix:** Consider making the QueryClient lifecycle more explicit by always creating it in `main.ts` and passing through Vue's provide/inject. The `getAppQueryClient()` function could throw if called before initialization rather than lazily creating.

---

### [LOW] Tight coupling between useRemoteWidget and QueryClient internals
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteWidget.ts:63-148
- **Issue:** The refactored `useRemoteWidget` now directly calls `queryClient.fetchQuery()` and `queryClient.invalidateQueries()`. This couples the widget logic tightly to TanStack Query's imperative API rather than using the reactive `useQuery` hook like `useRemoteOptions` does. This inconsistency means two different data-fetching patterns in the codebase.
- **Fix:** Consider whether `useRemoteWidget` could be refactored to use `useRemoteOptions` internally, or document why the imperative approach is necessary for this specific use case.

---

### [LOW] SpecAdapter abstraction not yet utilized
- **File:** src/renderer/extensions/vueNodes/widgets/adapters/specAdapter.ts:1-18
- **Issue:** The `SpecAdapter` interface with `canHandle`, `extractProps`, and optional `component` suggests an adapter registry pattern, but only `comboAdapter` is implemented and it's not used through a registry. The pattern is incomplete.
- **Fix:** Either complete the adapter registry pattern (create a registry that iterates adapters to find the right one) or simplify to direct function calls if only one adapter is needed. Avoid half-implemented abstractions.

---

### [MEDIUM] Breaking change: Removed test coverage for useRemoteWidget
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteWidget.test.ts (deleted)
- **Issue:** The entire 753-line test file for `useRemoteWidget` was deleted. While the implementation was refactored to use TanStack Query, removing all tests rather than adapting them to the new implementation leaves the legacy widget code path untested. The `useRemoteWidget` is still used in production (for `remote:` config).
- **Fix:** Add tests for the refactored `useRemoteWidget` covering the same scenarios as before: caching behavior, retry/backoff, auth headers, auto-refresh toggle, and concurrent access.

---

### [LOW] Leaky abstraction in RemoteRequestDescriptor
- **File:** src/platform/remote/schema/remoteRequestSchema.ts:3-11
- **Issue:** `RemoteRequestDescriptor` has `responseKey` as a string, but this implies knowledge of the response structure at the transport layer. This mixes data extraction concerns (which belong to the consumer) with request description (which should be transport-only).
- **Fix:** Consider moving `responseKey` handling to the `select` function in `useRemoteOptions` callers, keeping the descriptor focused on pure HTTP request description.

---

### [LOW] FormDropdownMenuItem props growing without clear structure
- **File:** src/renderer/extensions/vueNodes/widgets/components/form/dropdown/types.ts:49-54
- **Issue:** `FormDropdownMenuItemProps` now has `description` added, continuing growth of a flat props interface. The type mixes structural concerns (layout) with content concerns (name, label, description, previewUrl).
- **Fix:** Consider grouping related props, e.g., `content: { name, label, description }` and `media: { previewUrl }`, to improve organization as the interface grows.

---

### [CRITICAL] XOR validation not enforced at runtime
- **File:** src/schemas/nodeDefSchema.ts:127-136
- **Issue:** `zComboInputOptionsValidated` provides XOR validation between `remote` and `remote_combo`, but `zComboInputOptions` (without validation) is what's actually used in `ComboInputOptions` type and likely in runtime parsing. The validation schema appears to be test-only.
- **Fix:** Ensure `zComboInputOptionsValidated` is used in production parsing paths where node definitions are validated, not just in tests. Otherwise, invalid combinations could slip through.

---

### [LOW] Duplicate preview URL resolution logic
- **File:** src/base/remote/itemSchema.ts:35-51 and related usage
- **Issue:** `resolvePreviewUrl` handles URL normalization (absolute vs relative, data URIs, etc.). This logic may need to be shared with other asset URL handling in the codebase. Duplicating URL resolution logic risks inconsistency.
- **Fix:** Check if existing URL utilities in the codebase (e.g., asset service) could be reused, or extract this to a shared utility.
