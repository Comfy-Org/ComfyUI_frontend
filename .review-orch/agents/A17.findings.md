# A17 Structural Discipline Review: Derivable State, Impossible Types, Contracts

## Summary
Reviewed PR diff for remote combo widget feature. Found issues with derivable state patterns, potential impossible state combinations, and missing invariant enforcement.

---

### [MEDIUM] Redundant state synchronization between useRemoteCombo and modelValue
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:77-79
- **Issue:** The `selectedValue` field in the return object is just a pass-through of `args.modelValue`. The `select` function mutates `args.modelValue.value` directly. This creates two ways to access/modify the same state, increasing risk of synchronization issues if consumers use both paths.
- **Fix:** Consider returning only one access point. Either remove `selectedValue` from the return and have consumers use their own ref, or make `select` work through an emit pattern instead of direct mutation.

---

### [LOW] Stored state that could be derived: searchIndex
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:77-92
- **Issue:** `searchIndex` is a computed that builds a full Map on every `rawItems` change. While technically derived (computed), it pre-computes and caches the entire index eagerly. For large datasets, this could be expensive when search is not used.
- **Fix:** Consider lazy initialization (build index on first search) or memoize at the item level to avoid full rebuilds.

---

### [MEDIUM] RemoteComboContext allows impossible state combination
- **File:** src/renderer/extensions/vueNodes/widgets/components/RemoteCombo/state.ts:6-18
- **Issue:** The `RemoteComboContext` interface allows `isLoading: true` AND `errorMessage: non-null` simultaneously, which is logically impossible (you cannot be both loading and in an error state). The Trigger.vue component's `displayLabel` computed tries to handle this by checking `isLoading` first, but this is defensive coding around a poorly constrained type.
- **Fix:** Use a discriminated union for fetch state:
```typescript
type RemoteComboFetchState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success' }
```

---

### [MEDIUM] Missing invariant: Trigger disabled state inconsistent with aria-disabled
- **File:** src/renderer/extensions/vueNodes/widgets/components/RemoteCombo/Trigger.vue:50-55
- **Issue:** Both `disabled` and `aria-disabled` are computed with the same expression, but this creates redundancy and potential drift. If the logic changes, both must be updated in sync.
- **Fix:** Extract the disabled computation to a single computed property and use it for both attributes.

---

### [LOW] QueryClient singleton uses implicit mutable state
- **File:** src/platform/remote/queryClient.ts:11,21-24
- **Issue:** `appQueryClient` is a module-level mutable variable (`let appQueryClient`). `getAppQueryClient()` lazily creates and caches it. This pattern hides state and makes testing harder (tests must ensure cleanup between runs).
- **Fix:** Consider making the singleton more explicit, or use Vue's provide/inject with the app instance to scope the client lifecycle.

---

### [LOW] Redundant state: isOpen + isLoading + errorMessage vs single fetch state
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:32-34
- **Issue:** The composable maintains `isOpen` as a separate ref, while also tracking `isLoading` and `errorMessage` separately. The trigger's enabled/disabled state is derived from multiple independent booleans that could conflict.
- **Fix:** Consider a unified state machine approach where `isOpen` cannot be true while `isLoading` is true on initial fetch, preventing impossible UI states.

---

### [MEDIUM] Missing contract enforcement for RemoteItemSchema
- **File:** src/schemas/nodeDefSchema.ts:25-32
- **Issue:** The `zRemoteItemSchema` validates field presence but does not enforce that `value_field` and `label_field` must be valid dot-paths (no validation that they'll resolve against actual response data). Runtime errors occur silently when paths don't match.
- **Fix:** Add runtime warning or error in `mapToDropdownItem` when the path resolves to undefined for required fields (`value_field`, `label_field`).

---

### [LOW] Derivable previewType stored in context
- **File:** src/renderer/extensions/vueNodes/widgets/components/RemoteCombo/state.ts:18
- **Issue:** `previewType: ComputedRef<RemoteComboPreviewType>` is passed through context, but it's a static config value that doesn't change during the component lifecycle. This is not state that needs reactive tracking.
- **Fix:** Pass `previewType` as a plain prop or injection rather than a computed, reducing reactive overhead.

---

### [LOW] Auto-select logic doesn't guard against race conditions
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:107-118
- **Issue:** The `watch` on `items` calls `applyAutoSelect` with `immediate: true`. If items change rapidly (e.g., during refetch), auto-select could fire multiple times, potentially setting stale values.
- **Fix:** Guard `applyAutoSelect` to only run once per mount, or debounce the watcher to coalesce rapid item updates.

---

### [CRITICAL] Type allows empty id after mapping
- **File:** src/base/remote/itemSchema.ts:54-61
- **Issue:** `mapToDropdownItem` allows `id: ''` (empty string) when `value_field` path doesn't resolve. This creates items that pass type checks (`id: string`) but are functionally invalid. The `displayName` function falls back to `id` when `name` is empty, but an empty `id` renders nothing.
- **Fix:** Either throw/warn when `value_field` doesn't resolve, or use a sentinel value that's explicitly handled in display logic. Consider `id: string & { __brand: 'NonEmpty' }` for stricter typing.
