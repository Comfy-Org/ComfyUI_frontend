# C1 Regression Risk Review

## Summary

This PR introduces a new `RichComboWidget` component for remote-populated dropdowns using TanStack Query, alongside significant refactoring of the existing `useRemoteWidget` hook to use the same query infrastructure.

---

### [CRITICAL] Test File Deleted - Regression Coverage Lost

- **File:** `src/renderer/extensions/vueNodes/widgets/composables/useRemoteWidget.test.ts` (deleted)
- **Issue:** The entire test file for `useRemoteWidget` (753 lines) has been deleted. This file contained comprehensive tests for:
  - Cache management and deduplication
  - Exponential backoff and retry logic
  - Refresh behavior (permanent vs stale widgets)
  - Cloud authentication header injection
  - Auto-refresh toggle functionality
  - Concurrent access and race conditions
  - Error state handling and recovery
- **Fix:** The deleted tests covered behaviors that still exist in the refactored code. Either migrate relevant tests to new test files covering the TanStack Query integration, or retain tests that verify the preserved public API contract (e.g., `getValue`, `refreshValue`, auto-refresh toggle).

---

### [HIGH] Breaking Change - Removed Public API Methods

- **File:** `src/renderer/extensions/vueNodes/widgets/composables/useRemoteWidget.ts:196`
- **Issue:** The return object no longer exports `getCacheEntry` and `cacheKey`. Extensions or downstream code relying on these for debugging or custom cache inspection will break.
  - Old: `{ getCachedValue, getValue, refreshValue, addRefreshButton, getCacheEntry, cacheKey }`
  - New: `{ getCachedValue, getValue, refreshValue, addRefreshButton, getQueryKey }`
- **Fix:** If `getCacheEntry` was used externally, provide a migration path or document the breaking change. Consider exposing a `getQueryData` wrapper if cache introspection is still needed.

---

### [HIGH] Changed Backoff Algorithm

- **File:** `src/base/remote/retry.ts:6-7`
- **Issue:** The backoff algorithm changed from capped at 512ms to capped at 16000ms. The old code in `useRemoteWidget.ts` used `Math.min(1000 * Math.pow(2, retryCount), 512)` which appears to be a bug (caps at 512ms regardless of retry count). The new code uses `Math.min(1000 * Math.pow(2, retryCount), 16000)`. While this is likely a fix, it changes timing behavior that tests depended on.
  - Old: `getBackoff(1) = 512ms` (capped immediately)
  - New: `getBackoff(1) = 2000ms`, `getBackoff(4) = 16000ms`
- **Fix:** This is likely the intended behavior, but verify this timing change doesn't cause UX issues where users wait longer for retries.

---

### [MEDIUM] Removed Internal Cache State Tracking

- **File:** `src/renderer/extensions/vueNodes/widgets/composables/useRemoteWidget.ts`
- **Issue:** The refactored hook removes detailed cache state tracking (`isInitialized`, `isStale`, `isFetching`, `isFailed`, `isBackingOff`). The old code maintained explicit state about whether data was permanent, stale, or backing off. The new code delegates entirely to TanStack Query's staleTime and retry mechanisms.
- **Fix:** Verify that TanStack Query's default behavior matches the previous semantics for:
  - Permanent widgets (`refresh <= 0`) - old code prevented all refetches after first success
  - Stale detection timing
  - Backoff state persistence across widget instances

---

### [MEDIUM] Global QueryClient Singleton Pattern

- **File:** `src/platform/remote/queryClient.ts:5,15-19`
- **Issue:** The module uses a mutable module-level singleton (`let appQueryClient`). The `getAppQueryClient` function creates a new client if one doesn't exist. This pattern can cause issues if:
  - Tests don't properly isolate the singleton
  - The client is accessed before `createAppQueryClient` is called in `main.ts`
  - Multiple entry points create different clients
- **Fix:** Consider using dependency injection or Vue's provide/inject for the QueryClient. Alternatively, add guards to ensure `createAppQueryClient` is always called first.

---

### [MEDIUM] Missing XOR Validation at Runtime

- **File:** `src/schemas/nodeDefSchema.ts:127-135`
- **Issue:** The `zComboInputOptionsValidated` schema enforces XOR between `remote` and `remote_combo`, but it's unclear if this validated schema is used everywhere `zComboInputOptions` is used. The base schema still allows both fields.
- **Fix:** Verify that node definition validation in all code paths uses `zComboInputOptionsValidated` to prevent invalid configurations from reaching runtime.

---

### [MEDIUM] Auth Scope Partitioning Without Tests

- **File:** `src/platform/remote/queryKeys.ts:10-11`
- **Issue:** Query keys now partition by `workspaceId`, `userId`, and `apiKeyBucket`. If these values change during a session (e.g., user logs in/out, switches workspace), cached data may become stale or inaccessible without explicit invalidation.
- **Fix:** Add tests verifying cache behavior across auth state transitions. Consider adding cache invalidation on auth state changes.

---

### [LOW] Potential Audio Memory Leak

- **File:** `src/renderer/extensions/vueNodes/widgets/components/RemoteCombo/Item.vue:45-56`
- **Issue:** The audio preview functionality creates audio elements but doesn't explicitly release them when the component unmounts. While browsers generally handle this, rapidly scrolling through many audio items could accumulate unreleased audio resources.
- **Fix:** Add `onUnmounted` hook to pause and nullify audio element references.

---

### [LOW] Inconsistent Error Handling

- **File:** `src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:97-98`
- **Issue:** The `errorMessage` computed always returns a generic i18n message (`widgets.remoteCombo.loadFailed`) regardless of the actual error. The detailed error is logged to console but not surfaced to users.
- **Fix:** Consider categorizing errors (network, auth, parsing) and showing more specific messages, or at least logging structured error data for debugging.

---

### [LOW] Form Dropdown Changes May Affect Existing Components

- **File:** `src/renderer/extensions/vueNodes/widgets/components/form/dropdown/FormDropdownInput.vue:71-73`
- **Issue:** The label resolution logic changed from `item.label ?? item.name` to `item.label || item.name || item.id`. This means empty strings now fall through to the next field, which could change displayed labels for existing items where `label=""` was intentional.
- **Fix:** Verify this change doesn't affect existing dropdown usages. Consider using nullish coalescing (`??`) for label/name and only falling back to id as a last resort.

---

### [LOW] Missing Description Field in FormDropdownMenuItem Props

- **File:** `src/renderer/extensions/vueNodes/widgets/components/form/dropdown/FormDropdownMenuItem.vue`
- **Issue:** A new `description` prop was added to the component but the interface in `types.ts` already has it as optional. However, the component only renders description in list layout, not grid layout, which may be intentional but is undocumented.
- **Fix:** Document the layout-specific rendering behavior for the description field.
