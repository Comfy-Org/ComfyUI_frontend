# A4 Performance Review Findings

## Summary
Reviewed the diff for O(n^2) algorithms, unnecessary re-renders, missing memoization, bundle size concerns, and inefficient loops.

---

### [LOW] Linear Search in Trigger displayLabel
- **File:** src/renderer/extensions/vueNodes/widgets/components/RemoteCombo/Trigger.vue:31-32
- **Issue:** `ctx.items.value.find((i) => i.id === id)` performs O(n) lookup every time displayLabel is computed. If the items list is large and the trigger re-renders frequently, this adds up.
- **Fix:** Consider building a Map<id, item> as a computed property in the context/composable for O(1) lookups, especially if the items list can be large (hundreds of items).

---

### [LOW] Linear Filter in filteredItems
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:88-93
- **Issue:** `filteredItems` uses `.filter()` and `.includes()` on every search query change, resulting in O(n*m) where n is item count and m is search text length. For small lists this is fine, but could be slow for very large option sets.
- **Fix:** Acceptable for typical use cases. For 1000+ items, consider debouncing search or using a more efficient search algorithm. Current implementation is reasonable.

---

### [LOW] searchIndex Recomputation
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts:78-86
- **Issue:** `searchIndex` is computed by iterating all rawItems. It's correctly memoized via `computed()`, so it only recalculates when rawItems changes. However, the loop inside includes `buildSearchText` which joins array fields - this is O(n*k) where k is number of search fields.
- **Fix:** Current approach is correct. No action needed - the computed memoization prevents unnecessary recalculation.

---

### [INFO] Bundle Size Addition - @tanstack/vue-query
- **File:** package.json:77, pnpm-lock.yaml
- **Issue:** Adding `@tanstack/vue-query` introduces a new dependency. Based on bundlephobia data, vue-query adds ~12-15KB minified+gzipped to bundle.
- **Fix:** This is acceptable for the caching/query functionality it provides. The library is tree-shakeable and the benefits (automatic caching, deduplication, retry logic) justify the size.

---

### [INFO] msw Added as Optional Dev Dependency
- **File:** pnpm-lock.yaml
- **Issue:** `msw` (Mock Service Worker) appears as an optional dependency for vitest. This is a dev dependency and does not affect production bundle size.
- **Fix:** No action needed - dev dependency only.

---

### [INFO] QueryClient Lifecycle
- **File:** src/platform/remote/queryClient.ts:28-41
- **Issue:** The QueryClient is created as a module-level singleton with `gcTime: 5 * 60_000` (5 minutes). This means cached data persists for 5 minutes before garbage collection.
- **Fix:** This is reasonable. The comment correctly notes that auth-state changes tear down the layout, naturally evicting the cache. Memory usage is bounded.

---

### [INFO] Proper Use of Memoization
- **File:** src/renderer/extensions/vueNodes/widgets/composables/useRemoteCombo.ts
- **Issue:** The composable correctly uses Vue's `computed()` for derived state (items, filteredItems, searchIndex, errorMessage). This prevents unnecessary recalculations.
- **Fix:** No action needed - this is proper Vue reactivity usage.

---

### [INFO] Image/Audio/Video Lazy Loading
- **File:** src/renderer/extensions/vueNodes/widgets/components/RemoteCombo/Item.vue:76-77
- **Issue:** Images correctly use `loading="lazy"` and `decoding="async"` attributes for performance. Audio elements use `preload="none"`.
- **Fix:** No action needed - good practices are already in place.

---

## No Critical or Major Issues Found

The code follows performance best practices:
1. Proper use of Vue `computed()` for memoization
2. TanStack Query handles request deduplication and caching
3. Lazy loading for media assets
4. No O(n^2) algorithms detected
5. Bundle size increase is reasonable for the functionality added
