# ADR-RELEASES-PACKAGES-0033: SDK Packages Release Through Version-Bump PRs, Not Changesets

Date: 2026-09-16

## Status

Accepted

## Context

Three workspace packages are about to leave the monorepo and become npm
artifacts that a second repository installs:

- `@comfyorg/account-core` — the framework-free session core (session,
  billing transport, commands, readers).
- `@comfyorg/billing-contract` — the URL contract the hosted billing app
  shares with every Comfy product: the versioned route builder, the entry
  parser, and the closed `return_to` registry.
- `@comfyorg/ingest-types` — the TypeScript types and Zod schemas generated
  from Cloud's ingest OpenAPI specification, which `account-core` depends on.

`@comfyorg/account-ui` stays private for now. It is the Vue layer and has
exactly one consumer inside this repository; it becomes a fourth publishable
package only when a host outside the monorepo needs the components.

The consumer that forces the question is Platform (platform.comfy.org), a
separate repository with no pnpm workspace link into this one. It installs
these packages from the registry like any third party, so the version a
Platform engineer pins has to mean something. The same is true of
`apps/billing-web`, which is built here today but is a static SPA
([ADR-BILLING-WEB-0031](BILLING-WEB-0031-static-spa-boundary.md)) whose
dependency on the core is a package boundary, not a build-graph shortcut.

The monorepo already publishes one package to npm on exactly this pattern:
`@comfyorg/design-system`. A maintainer runs a `workflow_dispatch` that bumps
the version and opens a PR labelled `Release`; merging that PR triggers the
publish, the release-links comment, and a Slack notice. The pattern is two
years of habit for the team, the secrets and the label already exist, and
nobody has to learn anything new to cut a release.

Two forces pull the other way. The first is that three packages release
independently, and hand-driven bumps scale linearly with package count. The
second is `ingest-types`: it is regenerated by a bot in the Cloud repository,
which opens `[chore] Update Ingest API types from cloud@<sha>` PRs here
(#17226, #17396). Those PRs change a published package's contents without
touching its version, so today they would silently ship nothing.

Against that, the packages are pre-1.0 and their only external consumer is one
team we talk to daily. A release-automation tool bought now would be paid for
before the problem it solves exists.

## Decision

Release the three SDK packages through the same version-bump PR the
design-system uses, generalized over a `package` input instead of copied per
package. Do not adopt Changesets yet.

Four workflows carry it:

| Workflow                        | Trigger                                | What it does                                                                                                                         |
| ------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `version-bump-package.yaml`     | `workflow_dispatch`                    | Bumps one package on `main` and opens a `Release`-labelled PR titled `<package> <version>`                                           |
| `publish-package.yaml`          | `workflow_dispatch` + `workflow_call`  | Validates, builds, smoke-tests, and publishes one package with provenance                                                            |
| `publish-package-on-merge.yaml` | `pull_request: closed` on `main`       | On a merged `Release` PR, publishes every package whose version changed, writes the release links to an artifact, and posts to Slack |
| `pr-publish-report.yaml`        | `workflow_run` of the on-merge publish | Posts the release links to the Release PR, the only job on this path with write permission on pull requests                          |

Pre-merge snapshot publishing is a deliberate follow-up, not part of this
decision; the constraint that shapes it is recorded under Follow-ups.

The decisions inside those workflows:

- **One parameterized pair, not three copies.** `package` is a choice input
  over `account-core`, `billing-contract`, and `ingest-types`, mapped to its
  npm name by an explicit table so an unknown value fails loudly rather than
  publishing something unintended. The design-system workflows are left
  untouched; a fourth package joins by adding one line to two tables.
- **The `Release` label is the publish gate.** A merged PR that touches a
  package manifest publishes nothing unless a human attached the label, and
  the on-merge job compares each manifest's `version` against its first parent
  so a `Release` PR that edits a manifest for any other reason is inert.
- **The `private: true` latch is checked, not assumed.** The publish job fails
  with an explicit message while a package is still private. The latch came
  off the three manifests in the same reviewed PR that added these workflows,
  once the publish-readiness work (#17882) had proven the tarballs install
  from plain Node; the check stays so a package that re-enters the tables
  before it is ready fails loudly rather than shipping.
- **Build and smoke-test before publish, tolerantly.** The job runs `build`
  and `smoke:pack` with `--if-present` so it works both before and after the
  packaging PRs that introduce those scripts land. `pnpm publish` passes
  `--ignore-scripts`, so `prepack` cannot be relied on to produce `dist`.
- **`workspace:^`, not `workspace:*`, for internal dependencies.** pnpm
  rewrites the protocol at pack time: `workspace:*` becomes an exact pin,
  `workspace:^` becomes a caret range. A consumer that installs both
  `account-core` and `ingest-types` should get one copy of the schemas, and an
  exact pin makes that a lockfile conflict at the first divergent patch.
- **Prereleases go to `next`, releases to `latest`.** The dist-tag is derived
  from the version: a `-` after the patch segment means `next`. `latest` is
  never set by a workflow that a prerelease can reach.
- **Provenance is on for every publish.** Each publish runs under
  `id-token: write` with `--provenance`, so the npm page carries a signed link
  back to the workflow run and the commit. An external consumer installing an
  alpha of an auth package should be able to verify where the tarball came
  from.
- **No unmerged pull-request run reaches the registry credentials.** The
  on-merge path runs on the merge commit of a reviewed, `Release`-labelled PR,
  and the credentialed job refuses a `workflow_dispatch` on any ref but
  `main`, so a branch cannot hand `NPM_TOKEN` its own tree by pressing the
  button. A write-access holder can still edit that guard on a branch and
  dispatch it; the control for that is a protected publish environment with a
  branch rule, which this ADR does not yet claim.

### Versioning policy

- The hand-written packages — `account-core`, `billing-contract`, and
  `account-ui` when it joins — stay on `1.0.0-alpha.N` published to `next`
  until the Phase 7 host proof: Platform installs from the registry in a clean
  non-workspace checkout and `billing-web` runs a live top-up against it.
  `1.0.0` on `latest` is that proof's reward, not its precondition.
  `version-bump-package.yaml` enforces this rather than trusting the operator
  to pick the right increment: for those packages it accepts only a `pre*`
  increment with the `alpha` id, because `patch` on `1.0.0-alpha.0` is
  `1.0.0`, which the merge path would publish to `latest`. Promoting a
  package means amending this section and that gate together.
- `ingest-types` is outside that gate. It is a generated, runtime-free mirror
  of Cloud's ingest schemas, it is already at `1.0.0`, and its version is
  written by the regeneration bot in the Cloud repository rather than by
  anyone here — a prerelease line nothing in this repository can maintain. It
  ships `latest` from `1.0.x`.
- For the generated contract in `ingest-types`, a field or an endpoint being
  added is a minor; a field being removed, renamed, or changing meaning is a
  major. A human makes that call on the regeneration PR, because only a human
  can read a renamed field as "the same thing under a new name" or as "a
  different thing".
- `account-core` and `billing-contract` follow ordinary semver against their
  public exports, with `billing-contract`'s route version (`/v1`) as a second,
  independent axis: the package's major does not move because a new route
  version is added alongside the old one.

### Alternatives considered

**Changesets.** The obvious candidate, and the one to revisit. A contributor
writes a `.changeset/*.md` alongside the change, a bot maintains a "Version
Packages" PR, merging it bumps every affected package, writes CHANGELOGs, and
publishes. It solves the linear scaling and it solves the `ingest-types`
regeneration problem, since the bot PR could carry its own changeset. It is
not adopted now because its value is in the CHANGELOG and the multi-package
coordination, and there is no consumer asking for either: Platform is one team
reading the PR that changed the behaviour. Against that it adds a required
file to every PR touching `packages/`, a status check that fails on its
absence, and a second release surface for the team to learn while the
design-system keeps the first. Its own PR titles also collide with the
convention here, where the Linear ticket precedes the conventional prefix
(`FE-2218 ci(packages): …`); the bot's fixed "Version Packages" title has to
be configured around rather than accepted.

**release-please.** Derives versions from conventional commit prefixes and
maintains a release PR from them. The same objection lands harder: this repo's
titles put the ticket first, so the parser needs configuration before it reads
a single commit correctly, and the failure mode of a misparsed title is a
wrong version rather than a visible error. It also assumes the commit message
is the changelog, which is not how this repository writes commits.

**semantic-release.** Publishes straight off `main` with no human release
step. That removes the one property most worth keeping right now — a release
is a reviewable PR with a diff, a label, and a person who pressed the button —
for packages that hold the session and billing surface.

**A copied workflow per package.** Three near-identical files, three places to
fix the next bug in the publish sequence. Rejected on the same grounds the
monorepo was adopted ([ADR-DEVEX-MONOREPO-0002](DEVEX-MONOREPO-0002-adopt-a-pnpm-workspace-monorepo.md)).

## Consequences

### Positive

- The team already knows how to cut one of these releases; the only new input
  is which package.
- A release is a PR: reviewable diff, a label a human attaches, and a merge
  someone owns. Nothing reaches the registry from a push to `main`; the only
  other path is a `workflow_dispatch` of `publish-package.yaml` on `main`.
- Provenance and the `private` guard make the accidental-publish path explicit
  rather than a matter of care.
- Adding the fourth package (`account-ui`, when it goes public) is two table
  entries and one `paths` line.

### Negative

- Each release is a manual `workflow_dispatch`. Three packages released
  together are three dispatches and three PRs, and nothing enforces that they
  land in dependency order.
- No CHANGELOG is generated. A consumer asking "what changed in
  `1.0.0-alpha.4`" is pointed at a commit range, not at prose.
- Nothing yet couples a change in a package's contents to a version bump. A
  merged PR that changes `account-core` without touching its version publishes
  nothing, silently, which is the `ingest-types` regeneration gap below.
- The version-bump PR races the branch it bumps: a bump opened against `main`
  and merged after an unrelated package change still publishes the merge
  commit's tree, so the published contents can include work the bump author
  did not look at.
- There is no way to install a branch before it merges. Platform tries a
  contract change by merging it, or not at all, until the snapshot follow-up
  below lands.
- With `private` off, the `workflow_dispatch` path publishes whatever version
  `main` carries without a bump PR. It exists to re-run a publish the on-merge
  job missed, and it is the one release that no PR reviews; the protected
  publish environment noted under Decision is what would close it.

## Notes

### Sequencing

This ADR ships the release machinery and removes `private: true` from the
three manifests. It sits on the publish-readiness PR (#17882: files
allowlist, `dist` build with declarations, pack smoke test, private-utility
cut — the approach first drafted in #17838, #17839 and #17840), which in turn
sits on the `account-core` rename (#17851) and the Vue move (#17854). With
this merged, the remaining order to the first publish is bump and merge —
`ingest-types` first, because `account-core` resolves it as a caret range
from the registry, then `billing-contract` and `account-core`. `account-ui`
comes after `account-core` on the same reasoning once #17929 (its library
build) and #17932 (its dependency cut) have made it packable: `account-core`
is its one runtime dependency, resolved as a caret range from the registry,
so an `account-ui` published first is an artifact nothing can install.

### Follow-ups

- **`ingest-types` regeneration does not bump the version.** The generator
  lives in the Cloud repository, not here; the bot opens
  `[chore] Update Ingest API types from cloud@<sha>` PRs on the
  `update-ingest-types` branch. The change needed there is one step in the
  generating job, after the types are written and before the PR is opened:
  `pnpm -C packages/ingest-types version <patch|minor|major> --no-git-tag-version`,
  with the `Release` label added to the PR it opens. Until that lands, a
  regeneration ships to npm only if someone runs the bump workflow afterwards.
  Picking the increment is the human judgement described under Versioning
  policy, so the safe default for the bot is `patch` with a reviewer free to
  raise it on the PR.
- **Pre-merge snapshots ship separately.** A `pull_request` run executes the
  workflow definition from the pull request's own merge ref, so a publish step
  triggered that way is PR-authored code holding `NPM_TOKEN`. This would be
  the first `pull_request` path to the publish token in this repository, and
  the snapshot cannot be used at all until `private` comes off the three
  manifests, so it is not worth carrying that on the release path's timeline.
  The replacement publishes from a workflow that runs the default branch's
  definition — a `workflow_run` consumer of an artifact the pull-request job
  produces — or from a protected environment with required reviewers. It also
  has to answer a resolution question the release path does not: a snapshot of
  `account-core` in a PR that does not touch `ingest-types` resolves its caret
  range against the registry, so an unpublished `ingest-types` change can only
  be tested when the same PR touches both.
- **`account-ui` is the fourth candidate.** It joins the tables when an
  out-of-repo host needs the Vue layer. What makes it packable is open as
  #17929 and #17932; `private` stays on it until both land, and it publishes
  after `account-core` per the sequencing above.

### When to revisit Changesets

Any one of these is enough to reopen the decision:

- **Five or more published packages.** `account-ui` going public counts
  toward the five.
- **Frequent lockstep releases.** More than an occasional change that has to
  ship across two or three packages at once, where the manual order is a thing
  to get right rather than a thing that happens to be right.
- **A consumer asks for per-package CHANGELOGs.** Platform pinning a range
  rather than an exact version is the same signal.
- **The bump PRs become the bottleneck.** Releases waiting on someone to run a
  dispatch, or contents shipping late because nobody bumped.

Migration is additive rather than a rewrite: Changesets produces the same
shape this ADR builds — a bump PR that a human merges, and a publish that runs
on merge. Adopting it replaces the `version-bump-package.yaml` dispatch with
the Changesets bot and leaves `publish-package.yaml` and the on-merge trigger
in place, with the `Release` label swapped for the bot's own PR marker.
