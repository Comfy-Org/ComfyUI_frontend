# Billing Telemetry Initiative — Master Plan (incident-88)

**Scope:** Comfy-Org/ComfyUI_frontend @ `e1b25e7b0824` (main) · Comfy-Org/cloud @ `2f635ff` (`services/billing`) · `comfy-infra/terraform/datadog/monitor/` · PostHog project 204330 (prod) · Hex (unconfirmed)
**Date:** 2026-07-28

---

## 1. Overview

This advisory covers telemetry for the nine billing/subscription funnels active in Comfy Cloud today — new subscription (Flow 1), plan upgrade/downgrade (Flow 2), the destructive team→personal downgrade path (Flow 3), cancellation (Flow 4), resubscribe/win-back (Flow 5), credit top-ups (Flow 6), team invites and seat changes (Flow 7), and legacy-account provisioning (Flow 8), all fed by the shared paywall/upsell entry point (Flow 0). It matters right now because of **incident-88**, the ongoing billing incident: responders trying to answer "is money actually moving correctly end to end" have had to stitch together three disconnected views — frontend PostHog events, backend Datadog counters, and opaque Stripe-portal handoffs — with no shared identifier linking a user's attempt on one side to its outcome on the other, and with entire lifecycle stages (plan-change success/failure, cancel success/failure, resubscribe outcomes, the team-downgrade member-removal step) invisible in PostHog altogether. The recommendations below are organized so a backend or frontend engineer can pick a section and execute: a condensed map of what exists and what's missing, one prioritized alert backlog spanning all three tools, and per-tool setup instructions lifted directly from the underlying designs.

**Cross-cutting structural gaps** (apply to multiple rows above — escalate these before assuming any join can be built precisely):

1. `billingOperationStore.ts`'s `handleFailure`/`handleTimeout` never call telemetry for _any_ operation type — only `handleSuccess`, and only for `type==='subscription'`. Affects Flows 1b, 2b, 3, 6b.
2. Cancel, resubscribe, and plan-transition backend success paths write only to `billing_outbox`, never `billing_event` — PostHog has zero visibility into three of the highest-value lifecycle signals.
3. Datadog RUM has **no** billing instrumentation at all (`DatadogRumTelemetryProvider.ts` only tracks workflow-run duration) — PostHog is the sole frontend system of record today.
4. The external Stripe billing portal (legacy cancel and legacy upgrade/downgrade) is opaque on both sides — only "portal opened" is tracked.
5. No shared ID (e.g., `billing_op_id`) is threaded from any frontend event to its backend outcome anywhere in the system — every cross-repo join proposed below is a `workspace_id` + timestamp-window fallback until that ships.
6. PostHog has zero native alerts configured today (`/api/projects/204330/alerts/` is empty) — all existing threshold alerting lives in Datadog's 19 Terraform-managed monitors.

## 4. PostHog setup (project 204330)

**Before building anything:** go to **Data Management → Events**, search each event name below, and confirm the exact stored literal and 30-day volume — code-level constant names (e.g. `SUBSCRIPTION_REQUIRED_MODAL_OPENED`) may serialize differently in PostHog. Also confirm `reason`/`checkout_type` actually land as properties on `begin_checkout` before relying on a breakdown.

**Standard recipes** (reused across every flow below):

- **Recipe F — Funnel:** Insights → New insight → Funnels → add each step's event (use the step's **Properties** filter for property-scoped steps) → set **Conversion window** per flow (below) → set **Aggregating by: Unique users** (not sessions — BE events carry no session context) → add **Breakdown** if specified → Save, add to the consolidated dashboard.
- **Recipe T — Trend:** New insight → Trends → add series → for a ratio, toggle **Formula** and enter `A/B*100` → add breakdown if specified → Save.
- **Recipe A — Alert:** PostHog's native Alerts attach only to **Trends**, never Funnels — for any "funnel conversion rate" alert, build a companion ratio Trend first (Recipe T) purely to hang the alert on. Open the Trend → **Alerts** tab → New alert → set condition (greater/lower than, or anomaly mode if your instance's UI offers it) → threshold → check frequency follows the Trend's own interval → notification channel (Slack must be pre-connected under Project Settings → Integrations, one-time) → Save.
- For an OR-of-two-event-names step (e.g. two components firing different events for the same conceptual step), build a PostHog **Action** first (Data Management → Actions → New action → match both events), then use the Action in the funnel step.

3. **Per-flow notebooks, in this priority order** (matches where the PostHog gap is worst):
   - **a. Plan Transition Funnel (Flow 2/3)** — the audit's own "largest PostHog gap." Joins FE `begin_checkout{checkout_type:'change'}`/`MONTHLY_SUBSCRIPTION_SUCCEEDED` against `billing_outbox`'s `subscription_changed` rows (if reachable) to compute the upgrade/downgrade split neither PostHog nor Datadog can show today.
   - **b. Cancel & Resubscribe / Churn-Winback (Flow 4/5)** — a cohort/retention table (of workspaces that cancelled, % resubscribing within 7/14/30 days by tier) that's genuinely Hex-shaped (multi-step cohort SQL), directly answering the "only 2 of 12 PostHog cohorts touch billing" gap.
   - **c. Top-up Reconciliation (Flow 6)** — lowest effort, highest ROI: backend already emits everything needed (`commit_id`/`invoice_id`/`amount_cents` on every terminal branch) in PostHog itself, so this is closer to a pure PostHog/HogQL job. Hex's value-add is quantifying the size of Flow 6b's blind spot ("N completed top-ups/week with zero matching FE event") to build the case for the frontend fix.
   - **d. Invite → Seat Change (Flow 7)** — join `WORKSPACE_INVITE_SENT` against `team_billing:seat_added` on the documented fallback key (`workspace_id` + invited email + timestamp window), producing an invite-to-acceptance conversion rate and lag distribution that's answerable nowhere else.
   - Skip standalone notebooks for Flow 0 (pure PostHog, no join need), Flow 1a specifically (folds into the master selector), and Flow 8 (backend-only, no FE trigger to join against — a single Trend covers it).
4. **Alerting — scope narrowly.** Hex alerting (a scheduled notebook run → threshold on a cell's output → Slack/email) is real but is the wrong tool for anything Datadog's `op_terminal` already covers in near-real-time — PostHog's hourly batch-export cadence plus scheduled-run latency means a Hex alert is _at best_ ~1 hour stale. Use it **only** for reconciliation queries neither other tool can express (item #21 in the alert table): daily/hourly checks for FE start-events with no matching BE terminal signal within the flow's expected timeout window. Label these explicitly as "detects instrumentation/data gaps," never "detects live incidents," so nobody mistakes a stale Hex alert for the incident-response tool Datadog already is.

## 7. What can be automated (API/Terraform/code vs. click-through UI)

This changes how the team should sequence implementation — infra-as-code work can be reviewed and merged like any other PR; UI-only work needs a human with the right access clicking through a console, and that access isn't even confirmed to exist for one of these three tools.

**Fully automatable today:**

- **Datadog — everything in Section 5 except the RUM/member-removal prerequisites.** Dashboard widgets are `widget{}`/JSON-array edits inside the existing `datadog_dashboard`(`_json`) resource in `billing_health_dashboard.tf`. New monitors are `datadog_monitor` resource blocks appended to `billing_monitors.tf` (steady-state — never `billing_cutover_read_monitors.tf`, which is scoped to the temporary cutover migration). Log-based metrics are `datadog_logs_metric` resources. The RUM Application itself and RUM-based monitors are Terraform-manageable via `datadog_rum_application`/`datadog_monitor` once the frontend instrumentation lands. This is the most mature IaC surface of the three tools — prioritize it first since it's zero-risk to review and merge.
- **PostHog — Insights, Actions, Cohorts, and Dashboards.** `POST /api/projects/204330/insights/` gives full CRUD for both Funnels and Trends including breakdowns, formulas, exclusion steps (including the Flow 4 exclusion-event config — representable as an `exclusions` array with `funnel_from_step`/`funnel_to_step`), and conversion windows. `POST /api/projects/204330/actions/` covers OR-of-two-events steps. `POST /api/projects/204330/cohorts/` covers full behavioral cohort definitions. `POST /api/projects/204330/dashboards/` plus `"dashboards":[id]` on an insight payload attaches it. Auth: Personal API Key with `insight:write`/`dashboard:write`/`action:write`/`cohort:write` scopes as `Authorization: Bearer <key>`.
- **Hex — triggering and status-checking existing notebooks.** A REST endpoint exists to trigger a run of a published project and poll whether it succeeded, useful for kicking a reconciliation notebook from an external scheduler instead of relying on Hex's own cron, or firing a fresh before/after run right after a telemetry-fix deploy.

**Semi-automatable — API exists but the payload shape must be reverse-engineered:**

- **PostHog Alerts.** `GET/POST /api/projects/204330/alerts/` exists (the original audit used it to confirm zero alerts were configured), but the request/response schema is thin in public docs. Reliable path: create the first instance of each alert pattern via the UI, `GET` it back to capture the real field names (`condition`, `threshold`, `calculation_interval`, notification targets), then template the rest programmatically from that shape.

**UI-only, no way around it:**

- **Notification-channel wiring** for both PostHog and Datadog — Slack workspace OAuth connection and email routing are one-time console setup (PostHog: Project Settings → Integrations). The API can reference an already-configured target on a new alert but cannot create the Slack grant itself.
- **Hex notebook/app authoring.** There is no confirmed Hex API for creating a notebook, writing SQL cells, or building visualizations — construction is human-in-the-editor work; the API's job is operating already-built projects (run/schedule/status), not building them. Practically: someone (most plausibly Deep Mehta, pending confirmation he has workspace-admin rather than author-only access) has to hand-build the base-models and master notebooks in Section 6 before any API automation applies.
- **PostHog itself has no first-party IaC provider.** Community Terraform providers exist but aren't official. If declarative, code-reviewed management matters here as much as it does for Datadog, the realistic equivalent is a small idempotent create-or-update-by-name script against the REST API, checked into a repo and run in CI — not a Terraform-parity story. Set that expectation explicitly with anyone assuming PostHog will operate like the Datadog side.

**Net sequencing implication:** ship the Datadog Terraform PRs first (Section 5, item 1) — they're reviewable, mergeable, and touch nothing outside `comfy-infra`. Run the PostHog API script second, once event-name verification (Section 4's first line) is done by a human. Treat Hex as blocked on an access/ownership conversation with Deep Mehta and do not sequence any deliverable's timeline against it.

## 8. Architecture decisions (resolved 2026-07-28)

**1. RUM consolidation:** Datadog (RUM + backend APM/monitors) is the alerting/incident-response backbone going forward. PostHog remains the product-analytics/growth/exploratory layer (funnels, cohorts, feature flags, session recordings for human-driven analysis) — it is explicitly NOT the source of low-latency alerts, because PostHog Insights/Alerts run on an ETL/batch cadence unsuitable for incident response. The merged frontend PRs (#14111 + backports) did NOT do this — `DatadogRumTelemetryProvider.ts` still only implements `trackExecutionOutcome` and carries zero billing/product actions today; PostHog is the sole frontend system of record for billing telemetry as of this writing.

**2. IaC placement:** Datadog Terraform (monitors, dashboards) lives in the private `Comfy-Org/comfy-infra` repo, not in `ComfyUI_frontend` (public repo, untrusted-fork CI exposure makes it unsuitable for credentialed IaC). If colocation-for-review is wanted later, only inert config (JSON, no credentials, no apply logic) may live in the frontend repo, pulled read-only by comfy-infra.

**3. Remaining case for PostHog/Hex:** Yes — PostHog serves ~780 saved insights, 119 dashboards, 43 feature flags across Growth/Product/Marketing teams with no Datadog seats; closing the backend PostHog telemetry gaps is still required work independent of Datadog. Snowflake+Hex remains the tool for ad hoc, human-authored SQL joins across warehouse data that don't fit either tool's own model — informational/reconciliation use only, NOT real-time alerting (Hex's own latency is ~1hr+).

**4. Dual-emission rule (refined):** Default to RUM+Datadog for anything expressible as a raw event/count/ratio (covers nearly everything in this plan) — this is a low, one-time cost per event because the frontend's existing `TelemetryRegistry` (`src/platform/telemetry/`) already fans one call out to every provider. Reserve PostHog-native alerting only for genuinely cohort- or experiment-scoped signals, which have no RUM equivalent since cohort membership is computed by PostHog's own engine, not derivable from a single event stream.

**5. Frontend-side alerting is not purely an "error monitoring" concern:** funnel/flow step-to-step drop-off (e.g. onboarding conversion regression across a release) is a legitimate Datadog-RUM-alertable signal once the relevant events are dual-emitted — the split is about where the ALERT is configured, not whether the underlying signal "looks like" a product statistic or a hard error.
